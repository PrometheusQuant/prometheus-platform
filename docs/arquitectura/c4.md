# Diagramas C4

Vistas del [modelo C4](https://c4model.com/) de Simon Brown, dibujadas con Mermaid para que se
versionen como texto junto al código.

!!! note "Estado al 22-nov-2026"
    Los diagramas describen el **sistema que existe hoy**. Lo que todavía no existe va en gris y
    punteado, con el ticket que lo construye. La primera versión (octubre) describía la arquitectura
    objetivo; las diferencias con lo construido se explican al final.

## Nivel 3: componentes del runner de paper

El runner es el contenedor que decide y opera. Cada flecha cruza un puerto de
[`domain/ports.py`](../arquitectura/estructura-de-directorios.md): los adaptadores se cambian sin tocar
el núcleo. Por ejemplo, el bróker simulado se reemplazará por Binance Demo en PQ-52.

## Flujo de una orden

Un ciclo del runner, de la señal a la alerta. Así es en el código (`api/paper/runner.py`).

```mermaid
sequenceDiagram
    autonumber
    participant R as Runner (tick)
    participant K as Kill-switch
    participant M as Mercado (WS/REST)
    participant S as Estrategia (carry)
    participant RM as Riesgo
    participant J as Diario
    participant B as Bróker simulado
    participant T as Telegram

    R->>K: observe()
    alt kill-switch activado
        K-->>R: activado (cancela órdenes abiertas)
        R->>B: órdenes de cierre (reducir siempre se permite)
    end
    R->>M: precios de spot y perpetuo
    R->>RM: monitor(cartera) + señales de contraparte
    alt violación grave (pérdida diaria, apalancamiento, pata sin cubrir)
        RM->>K: trip(motivo)
        K->>J: KillSwitchTripped
        K-->>T: alerta CRITICAL
    end
    R->>S: liquidación de funding nueva
    S-->>R: decisión: entrar, mantener o salir (la misma regla del backtest)
    R->>J: FundingSettled con el estado deseado
    Note over R: espera la latencia pre-registrada (t + 1 h)
    R->>RM: pre_trade de TODAS las patas
    alt alguna pata rechazada
        RM-->>R: rechazo
        R->>J: RiskLimitBreached (no se envía ninguna pata)
    else todas aprobadas
        R->>J: OrderSubmitted
        R->>B: submit(orden)
        B-->>R: fill con comisión y slippage
        R->>J: OrderFilled
    end
    R->>J: PortfolioValued
    R->>R: heartbeat en disco (lo lee el vigilante)
    opt cambio de día UTC
        R-->>T: resumen diario
    end
```

**Por qué es seguro reiniciarlo:** el runner trabaja **por niveles**. El estado deseado queda en el
diario, y cada ciclo reconcilia las posiciones con él. Una caída entre dos patas se corrige en el
ciclo siguiente, y el kill-switch sobrevive a un reinicio porque es un archivo.

**Dónde va a correr:**

- **Oracle Cloud Always Free:** VM A1 de 1 OCPU y 6 GB en `sa-bogota-1`. Se reintenta
  automáticamente hasta que Oracle tenga capacidad ([runbook](../runbooks/oracle-cloud.md)).
- **AWS:** cuenta en revisión, región São Paulo, como alternativa.

**Reglas para cualquier servidor:**

- ninguna región de EE. UU., porque Binance bloquea esas IP;
- solo el puerto 22 abierto;
- el servidor solo tiene la clave **pública** de los respaldos.

## Correspondencia con los módulos (ADR-0001)

| Contenedor | Paquetes de `prometheus_platform` |
|---|---|
| CLI `pq` | `api` → `data_platform`, `research`, `adapters` |
| Orquestador | `api/orquestacion` → `data_platform`, `adapters` (Data Vision, REST, bronze) |
| Runner de paper | `api/paper` → `strategies`, `execution`, `portfolio_risk`, `adapters` (mercado, bróker, diario) |
| Vigilante y bot | `api/paper` → `adapters` (diario, Telegram) |
| Dashboard | `api/dashboard` (solo lectura) |
| Informes y página pública | `api/report` → `research` y los artefactos |
| Todos | `domain` (núcleo y puertos) y `ops` (configuración, logging y alertas) |

Las reglas de dependencia entre paquetes están en
[Estructura de directorios](estructura-de-directorios.md) y se verifican en CI con
`import-linter`.

## Qué cambió respecto de la arquitectura objetivo de octubre

| Objetivo (octubre) | Lo construido | Por qué |
|---|---|---|
| PostgreSQL para el diario de eventos | JSONL append-only en disco | Un solo escritor y pocos KB al día: no justifica un servidor de base de datos. Se respalda cifrado cada hora |
| NautilusTrader en el proceso live | Runner propio con bróker simulado | Paridad exacta con el backtest y sin esperar las claves (PQ-17). ADR-0006 sigue en propuesta hasta el spike PQ-51 |
| MLflow con PostgreSQL | `mlflow-skinny` con SQLite y registro JSONL en git | N tiene que sumarse entre máquinas: el registro en git lo comparte (PQ-112) |
| Grafana para operar | Dashboard de Streamlit, alertas y bot de Telegram | Llegan al celular sin servidor; Grafana queda para PQ-71 |
